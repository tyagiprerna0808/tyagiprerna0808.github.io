Part 1 of Vibe Coding & Agents — my notes from Google's five-day intensive (May 2026). This one covers The New SDLC With Vibe Coding by Addy Osmani, Shubham Saboo and Sokratis Kartakis.

I came into this expecting a sales pitch for coding agents. What I got instead was the clearest argument I've read for why the model is not the interesting part, and I've been rearranging how I work ever since.

Here is the line that reframed it for me: an agent that does something wrong is usually not a model failure. It's a missing tool, a vague rule, an absent guardrail, or a context window stuffed with noise. Most agent failures, examined honestly, are configuration failures.

That is a very familiar feeling. I spent three years on fraud and AML models where almost every "the model is wrong" escalation turned out to be a feature computed differently in two places. Same disease, new host.

Vibe coding is a spectrum, not a verb

Karpathy's original February 2025 framing — give in to the vibes, forget the code exists — went viral because it named something people were already doing. Then it got applied to everything, and stopped meaning anything. By early 2026 he'd added a second term, agentic engineering, for the disciplined end.

The paper's move is to stop treating these as a binary and lay them out as endpoints:

Vibe coding Structured AI-assisted Agentic engineering
Intent Casual prompts Detailed prompts with examples and constraints Formal specs, architecture docs, memory files
Verification "Does it seem to work?" Manual testing, spot-checks Automated suites, CI/CD gates, LM judges
Codebase understanding May not read the output Selective review of critical paths Architecture reviewed; AI handles details
Error handling Paste the error back in Human diagnoses, AI implements the fix Agents self-diagnose within defined bounds
Scope Prototypes, hackathons Features in established codebases Production systems, team scale
Risk High — fine for disposable code Moderate Low — systematic verification at every stage

The differentiator isn't whether you use AI. It's how much structure, verification and human judgment surrounds the output. And the single sharpest axis is that verification row.

Tests and evals are not the same instrument. Tests verify the deterministic parts: this input produces that output, checked by code. Evals verify the parts that aren't deterministic: did the agent take a sensible trajectory, choose the right tools, clear the quality bar — checked by labelled datasets, rubrics and LM judges. Without both, it's vibe coding no matter how elaborate the prompts are.

I like this because it kills a rhetorical move I've watched people make. "We're not vibe coding, our prompts are really detailed." Detailed prompts are not verification. If nothing checks the output, the sophistication of the input is decoration.

Agent = model + harness

The central claim of the paper, and the one worth arguing about: a raw model is not an agent. It becomes one when a harness gives it state, tool execution, feedback loops and enforceable constraints. Everything you actually experience using Claude Code, Cursor, Codex, Antigravity, Aider or Cline is dominated by the harness, not by which model is underneath.

What's in the harness:

  • Instructions and rule files — AGENTS.md, CLAUDE.md, GEMINI.md, skill files, sub-agent prompts
  • Tools — functions, MCP servers, APIs, and the prose that tells the model when to reach for each one
  • Sandboxes — where the code runs, what it can touch, what it can't reach
  • Orchestration logic — sub-agent spawning, model routing, hand-offs
  • Guardrails and hooks — deterministic code at lifecycle points: before a tool call, after a file edit, before a commit. This is where you put the things the agent should never forget but reliably does.
  • Observability — logs, traces, evals, cost and latency metering

Two benchmark results in the paper make this concrete rather than philosophical. On Terminal Bench 2.0, one team moved a coding agent from outside the Top 30 into the Top 5 by changing only the harness, with no model change. Separately, LangChain raised an agent's score on the same benchmark by 13.7 points by tweaking only the system prompt, tools and middleware around a fixed model.

The uncomfortable corollary is in the paper too: that surface area is the team's, not the model provider's. Nobody ships you a good harness.

Context engineering is the actual skill

Six types of context every agent needs: instructions (role, goals, boundaries), knowledge (retrieved docs, diagrams, domain data), memory (session logs and persistent project state), examples (few-shot demos, reference patterns), tools (precise definitions), and guardrails (hard constraints, formats, safety validations).

The engineering decision is which of those the agent carries upfront versus retrieves on demand:

  • Static context is always loaded — system instructions, rule files, global memory, persona. It defines who the agent is. It's expensive because every token is present in every interaction whether it's relevant or not.
  • Dynamic context is loaded on demand — skills triggered by task matching, tool results, RAG documents, windowed history. You pay the token cost only when you need the information.

Too much static context wastes tokens and dilutes signal. Too little and the agent forgets the rules that matter. The paper's recommendation is to treat that boundary as a first-class architectural decision, reviewed and versioned like any other config — and the pattern for managing the dynamic half at scale is Agent Skills, which gets its own paper on Day 3.

The question isn't "how do I trick the AI into writing good code?" It's "what would a new team member need to know to contribute effectively, and how do I encode that knowledge in a form the AI can use?"

That reframe is the whole game. Everything I've since put in an AGENTS.md came from asking that question and writing down the answer.

Conductor or orchestrator

Two modes, and good developers move between them fluidly rather than picking one.

Conductor is hands-on and real-time. You're in the editor, watching code appear, correcting as you go. Right for complex logic, tricky debugging, unfamiliar codebases where you need to understand each change as it lands. The risk: if you're personally directing every keystroke, you are the throughput ceiling.

Orchestrator is async delegation. You define goals, hand them to agents that may be running in parallel in the background, and review results. Right for bug fixes, features against established patterns, migrations, test generation. It demands a different skill set — specification (precise enough to execute unambiguously), decomposition (right-sized units), evaluation (fast judgment on whether output clears the bar), and system design (the constraints and feedback loops that keep agents productive).

The paper maps three places coding agents show up in a day: in the editor (inline completion, chat panels — Copilot, Cursor, Windsurf), in the terminal (multi-file work, running tools and tests, iterating on results — Claude Code, Codex CLI, Antigravity CLI, Cline), and in the background (cloud sandboxes, hours at a time, a pull request as output — Jules, Copilot agent mode, Cursor background agents). Most people use all three in one day, and the right starting point is the task, not whichever sits highest on some autonomy ladder.

The 80% problem, and the METR number

Agents generate roughly 80% of a feature fast. The remaining 20% — edge cases, error handling, integration points, subtle correctness — needs contextual knowledge current models often don't have.

And the errors have changed character. They used to be syntax. Now they're conceptual: wrong assumptions about business logic, no request for clarification on ambiguous requirements, missed edge cases, architectural choices that quietly become maintenance debt. These are harder to catch because the code looks right and may pass basic tests.

Industry surveys report 25–39% productivity gains. But a METR study found experienced developers using AI assistants took 19% longer on certain tasks — largely time spent verifying, debugging and correcting output. AI doesn't remove implementation work so much as convert it from writing into reviewing, guiding and verifying.

Both numbers can be true. That's the point. The gain depends entirely on how much of the verification you've automated, which takes you straight back to the harness.

The economics nobody puts in the demo

My favourite section, because it's the one that translates into a conversation with someone who controls a budget.

Vibe coding is low CapEx, high OpEx. Entry cost is a subscription. The compounding costs are the token burn rate (dumping unstructured files into context and repeatedly asking the model to fix its own unverified mistakes — an expensive prompting loop with a low first-pass success rate), the maintenance tax (six months later a human spends days reverse-engineering AI-generated spaghetti), and security remediation (fixing a flaw in production costs exponentially more than catching it at design).

Agentic engineering is high CapEx, low OpEx. You pay upfront — API schemas, deterministic test suites, structured context — and the marginal cost of shipping and maintaining each feature drops.

Which makes context engineering a financial lever, not just a technical one. A dense, high-signal payload raises first-pass success and avoids the trial-and-error loops. And a well-designed factory routes deterministic, lower-complexity work — test generation, code review, CI monitoring — to smaller, cheaper models, instead of paying frontier prices to fix a typo.

What I actually changed

The paper's advice for individual developers is a short list, and I've been working through it rather than nodding at it:

  1. Set up an AGENTS.md. Ten lines to start: stack, conventions, hard rules, workflow. Add a rule every time the agent does something it shouldn't do again. Mine grew fastest from the second half of that sentence.
  2. Write the tests and evals before generating the code. They are the contract. A good eval suite communicates intent more precisely than any prompt, and it's the thing that moves you along the spectrum.
  3. Review every line that ships. Be suspicious of anything clever. Check imports resolve to real packages. Verify error handling covers realistic failures.
  4. Keep your own skills sharp. AI handling the routine only works if debugging, system design and intuition for correctness stay strong. It's leverage on expertise, not a replacement for it.

The framing I'm keeping: in the factory model, your primary output is no longer code. It's the system that produces code — specs, agents, quality gates, feedback loops, guardrails. A factory manager doesn't assemble every widget. They design the line and own the quality control.
