Part 5 of Vibe Coding & Agents. Notes on Spec-Driven Production Grade Development in the Age of Vibe Coding by Lee Boonstra — and the one with the best horror story.

Start with the horror story, because it earns the rest of the paper.

A developer asked an agent to create a button, with the built-in browser running in YOLO (auto-approve) mode. The browser agent autonomously clicked the new button. The button was meant for an email agent. No URL was specified, so the agent filled the gap with whatever strings were in its context and connected to a deprecated legacy agent with no email safeguards.

Fifty colleagues received emails full of hallucinated content.

The lesson isn't "email is dangerous". It's that the agent was doing exactly its job — fulfilling a directive with the data available, with no check on whether it should. Without a human in the loop or a policy engine, an autonomous system optimises for its goal using whatever it can find. Context hallucination isn't the model being stupid; it's the model being obedient with insufficient information.

"Vibe coding" is not "vibe in production"

The framing distinction this paper opens with. You can use agents to their full potential and still have everything fully intended and controlled. What that requires is inverting where your time goes.

The claim that took me a minute: code is now disposable. With a rock-solid spec you can regenerate the codebase repeatedly — flip a project from Python to JavaScript in an afternoon. And because it's disposable there's no emotional attachment. You haven't spent twelve hours debugging a semicolon, so you don't fear throwing it away when requirements change.

Which relocates the developer from coder to technical architect, and makes the spec the artifact you actually maintain. Give an LLM a vibe instead of a blueprint and it will guess — and in enterprise software, guessing is how rogue-agent incidents happen.

A production-grade spec is an architectural north star. It lives in the repo — typically Markdown or YAML in a specs/ folder — and it's the source of truth for humans and agents alike. It contains the full technical design (not "make a login page" but requirements, database schemas, API contracts), visual aids and pinned library versions, the why behind the what, and scenarios: what good looks like, what wrong looks like, and the edge cases.

The author's own workflow: write the technical design in a doc, get it reviewed by humans, then export to Markdown into specs/. You would much rather a human catch a logic flaw in the design than discover it after the agent has generated thousands of lines around it.

The format tax

This was the most surprising, most immediately actionable finding in all five papers.

A 2026 study by Ouyang et al. (SkCC: Portable and Secure Skill Compilation for Cross-Framework LLM Agents) found LLM agents are extremely sensitive to how instructions are formatted — up to a 40% performance drop from generic, unoptimised Markdown.

The recommended strategy for Gemini is hybrid: clean Markdown headers to anchor attention, switching to YAML for structured configuration or data schemas nested more than three deep. The measured parsing accuracy on deeply nested configuration:

Format Parsing accuracy on deeply nested config
YAML 51.9%
JSON 43.1%
XML 33.8%

So: narrative instructions in Markdown, deeply nested specifications in YAML, and you skip the reasoning tax that heavy JSON inputs impose. Note that even the winner is barely above a coin flip — the real lesson may be to stop nesting four levels deep in a file you hand to a model.

The underlying discipline is treating tokenization as a hard physical constraint. Every character, newline and indentation space translates into budget and latency, multiplied across every turn of a multi-step reasoning loop. Your specs/ folder isn't documentation. It's a compiled instruction set.

Where instructions live

Dumping a hundred-page design doc into a chat window exhausts the context budget, raises latency and fragments the context. Four homes, four lifetimes:

  • Chat interface — ephemeral, session-specific. Use it purely for orchestration and fast feedback: "Review the design in specs/payment_retry.md and generate the failing unit tests defined in Scenario 3."
  • The specs/ folder — task-specific, checked into version control. Technical design, BDD scenarios, API contracts, YAML schemas. The agent indexes it instead of you prompt-stuffing.
  • Agent skills — reusable, behaviour-focused, trigger-based. Repeatable engineering habits, like maintaining a CHANGELOG.md whenever code changes.
  • System prompts — global, identity-focused, layered hierarchically: a global profile in the home config for personal defaults, a shared cross-tool AGENTS.md so a team using multiple clients doesn't fragment its instructions, and a project-root file that takes highest priority.

For the spec content itself, BDD in Gherkin — Scenario / Given / When / Then — forces the model to think in state → action → outcome, which is precisely the structure that stops it improvising.

Four modes, four mindsets

The Architect (project generation). No YOLO mode. Explicitly prompt the agent not to code immediately — propose folder structure and tech stack first, for confirmation. Include tests, documentation and logging in the generation. Pin version numbers for every library.

The Builder (feature generation). Match the existing style — naming patterns, error handling. Confirm multi-file changes manually. Read the diff.

The Forensic Specialist (bug fixing). The most transferable advice in the paper: shift from symptom prompting ("the button doesn't work") to evidence prompting ("logs pulled with gcloud logging read 'textPayload:ERROR' --limit 5 showed a 403"). Then explain the flow: request hits load balancer → auth strips header → pod fails. Always ask for a failing test or a curl that reproduces the bug first, and keep it in the codebase so the bug can't come back. Constrain the agent to the root cause only — no opportunistic cleanup, because it wrecks the review.

The Author (documentation). In spec-driven development the docs are the source of truth; when docs and code drift apart the AI starts hallucinating. Encode "keep the README and CHANGELOG current" as a skill.

Watch for downgraded versions. Agents suggest older library and model versions because nothing newer existed at their training cutoff. Counter it with docs in the spec folder, RAG on current documentation, or a line in the profile prompt — and double-check every version number an agent proposes. Also: let it rename variables, but as a separate task, never inside a bug fix.

What happens to the team

Bolting agents onto a twenty-year-old workflow is a jet engine on a horse-drawn carriage. Three failure categories show up fast:

  • Merge conflicts — multiple developers landing in the same file within the hour.
  • Review gridlock — a huge PR becomes a Russian doll of sub-PRs; #1 can't merge without #2, which needs #3, which is blocked by a reviewer in another timezone.
  • Context fragmentation — a teammate renames a variable in a shared file; an agent working from an outdated snapshot generates code calling a function that no longer exists.

The proposed adaptations, which read as genuinely new process rather than warmed-over Agile:

  • Bundled summaries and risk assessments. Every PR carries an AI-generated snapshot of what changed, potential breakage points, and a risk assessment — so humans spend attention on architectural impact instead of getting lost in lines.
  • Reimagined ownership. Human review shifts from nitpicking style on disposable agent-written code to guarding the integrity of the architectural blueprint. Style goes to linters and a shared stylebook.
  • Conditional LGTM. A reviewer approves contingent on tests passing; green means it merges automatically. This alone kills the twelve-hour cross-timezone stall.
  • No-blame culture. In high-velocity environments the person producing the most code becomes the scapegoat for every bug and conflict. Attribute these to broken integration processes, not to the individual using the agent.
  • Split work so people rarely touch the same files — clear ownership over APIs versus UX, with a designated part-owner handling synchronisation when overlap is unavoidable.

Reviewers that run themselves

You can write an excellent review prompt. The question is who runs it on every PR without a human pushing a button. Three tiers, differing in who owns the runtime and who writes the criteria:

  • Tier 1 — Managed. Enable a SaaS PR reviewer on the org and every PR gets commented on. No prompts, no infrastructure. The trade: you get the vendor's opinions, which will miss what matters to a house style or a domain risk profile.
  • Tier 2 — Hybrid. Write your own review skill, commit it, trigger it from a CI action running a coding-agent CLI in non-interactive mode, post the result as a PR comment. Runtime belongs to CI; prompts, model choice, sandboxing and criteria belong to you. The paper calls this the right starting point for most teams and I agree.
  • Tier 3 — Custom. A fully owned agent with durable sessions and memory, wired to webhooks. Right when the reviewer must hold context across a multi-PR refactor or decompose "audit this service for compliance drift" into a hundred sub-tasks. You also own evaluation, observability, cost, and the on-call rotation.

Three questions pick the tier: how specific are your criteria, does the agent need memory across runs, and what's the worst case if it's wrong (a noisy comment — any tier; a merged regression or a leaked secret — Tier 3 with a policy server in front of every tool call).

The example that makes it concrete: a fintech platform team started on Tier 1 and found their compliance reviewer flagging boilerplate auditors had already signed off, while missing the one thing that mattered — unmasked PII in log statements. A 40-line compliance-check.md wired to a CI action dropped the false positives sharply within a week. They've never needed Tier 3.

That's the shape of the whole paper's advice: pick the lowest tier that catches what matters.

At the far end, Tier 3 at full scale stops being a PR watcher and becomes something that understands the system the PRs live in — code, docs, tickets and design documents ingested into a knowledge graph, with agents combining graph traversal for structural queries ("every function that transitively calls payment.process()"), vector search for semantic ones, and full-text for exact identifiers. Flatten a codebase into a vector store and you lose the structure that makes code legible. On million-line codebases, pilots have moved equivalent refactor work from two weeks to a few hours.

Approval fatigue is a real number

Quantum Workplace research reported by CNBC: frequent AI users are 45% more likely to experience high burnout than non-users.

The mechanism is a constant stream of micro-approvals — improve a line, adjust a tool call, confirm a diff — until people start clicking Approve reflexively. It's low-grade exhaustion where the team stops checking the machine's work in order to keep up with its pace. Which is exactly the condition every control in the Day 4 paper depends on not happening.

The suggested countermeasures are structural rather than motivational: digital quiet hours so approval requests don't bleed into evenings and weekends, and weekly agent insight sessions where developers share patterns their agents surfaced, turning isolated discoveries into shared knowledge.

Where this leaves me

Five papers, and the argument holds together better than I expected it to. The thread:

  1. The model is the commodity; the harness is the product (Day 1).
  2. The harness reaches the world through open protocols, or it drowns in bespoke wrappers (Day 2).
  3. Inside the harness, the reusable unit of capability is a skill — and an untested one can make things worse (Day 3).
  4. Security bounds what the agent may do; evaluation judges whether it's worth shipping. Both (Day 4).
  5. None of it survives team scale without a spec, and a review process rebuilt for the new volume (Day 5).

What I'm actually doing about it: an AGENTS.md that grows a rule every time an agent does something I don't want repeated. A specs/ folder before a src/ folder. Evals written before the thing they evaluate. And a standing suspicion of any output that looks right and hasn't been checked by anything but me.

Which is, uncomfortably, the same discipline that production ML always needed. The tooling got dramatically better. The failure mode did not change at all.
