Part 4 of Vibe Coding & Agents. Notes on Vibe Coding Agent Security and Evaluation.

The organising sentence of this paper is worth memorising, because it separates two things that constantly get collapsed into one:

Security tells you if the agent stayed inside the boundary. Evaluation tells you whether what happened inside that boundary is actually worth shipping.

An agent can pass every security check and still misread the intent, ignore the project's conventions, and quietly break an unrelated feature. Both halves are required. Most teams I've seen build one and assume it covers the other.

Why the old trust model doesn't fit

In deterministic software, trust is binary: the code compiles, the tests pass, the credentials are valid. In an agentic system you have a non-human workforce with ambient agency — it can execute generated code, hit sensitive internal APIs, and modify production environments.

Static identity is a poor perimeter for that. An agent can hold a perfectly valid access token and operate with misaligned intent. So the paper replaces the pass-once gate with Effective Trust: a continuous metric evaluated across supply chain, identity, runtime behaviour and contextual associations. Trust is earned continuously, not granted at deploy time. The model shifts from identity-as-perimeter to context-as-perimeter.

The baseline is a seven-pillar architecture, each with an owner:

Pillar The threat The control
1 · Infrastructure Container escape, upstream poisoning Ephemeral kernel-level sandboxes (gVisor), strict egress governance
2 · Data Context leakage, poisoned RAG, cross-tenant vector poisoning CMEK at rest, mTLS in transit, scoped access, strict tenant partitioning in vector stores
3 · Model Semantic attacks subverting instructions Treat system instructions and prompt templates as cryptographically attested artifacts
4 · Application & runtime Autonomy misused during tool calls LLM firewalls, deterministic hooks at lifecycle points, a centralised agent gateway
5 · IAM The confused deputy Unique cryptographic identities (SPIFFE), ABAC, JIT token downscoping
6 · Observability & SecOps Invisible failures, silent drift OpenTelemetry, agent behavioural analytics, Red/Blue/Green triad
7 · Governance Unattributable autonomous decisions EU AI Act impact assessments, immutable audit trail, risk-stratified attestation

The line that stuck: if generated code compiles without errors, developers assume it is safe. The governance answer is to replace approval buttons with mandatory logic reviews that translate the syntax back into plain language.

Slopsquatting

My favourite new threat name and a genuinely elegant attack. Language models hallucinate package names that don't exist. Attackers monitor developer forums and AI outputs for those hallucinations, then publish malware under the exact fake names. Because autonomous agents alter dependency graphs without human confirmation, one hallucination pulls malware straight into the build.

Wiz calls it slopsquatting. The defence is unglamorous: source dependencies exclusively from vetted providers or internal registries, enforce cryptographic version pinning, and have CI verify SBOM entries and signatures via binary authorisation before anything reaches production.

The adjacent one is repository poisoning — zero-width Unicode characters and homoglyphs sitting in a codebase, invisible to human review. Because agents replicate code far faster than humans, one hidden payload can spread across hundreds of files in minutes.

What vibe-coded apps get wrong, predictably

Two failure shapes, and the paper says them plainly: generated code trusts the browser too much and leaves the backend wide open.

AI generation takes the path of least resistance and handles sensitive operations on the frontend — API keys, password validation, session flags dumped into the client. Anyone with devtools open can read the credentials or edit their own access level. And the speed of building outpaces the invisible security layers: the tools happily connect a database or spin up an admin dashboard, but rarely enable default-deny access controls, so row-level security gets skipped and staging environments sit on the public internet.

The enforcement design is the part I think is genuinely well judged. Hard-blocking insecure prompts inside the IDE is easily bypassed and creates friction for people doing legitimate work. So: advisory linters in the IDE for real-time guidance, unyielding deterministic enforcement in CI/CD — SAST and SCA scanning everything before it reaches production. Advice where it's cheap, gates where they're binding.

Zero ambient authority, and the Vibe Diff

The confused deputy problem: a prompt injection — say, a malicious instruction hidden in an open-source repo someone pasted into their context window — tricks an over-privileged agent into executing a command on the attacker's behalf.

Three controls stack against it:

  1. A distinct agentic identity. The agent must never operate under the human's delegated credentials, which grant it dangerous ambient access. It authenticates as something explicitly tagged agentic, so permissions stay bound and auditable.
  2. JIT downscoping. When the agent writes a new script, the sandbox gets fresh, hyper-restricted credentials scoped to exactly the data sources that script needs — not the parent's broad permissions — and they expire the moment the task ends. Plus file-tree allowlists with deny-by-default on secrets, build scripts and production manifests.
  3. Elicitation with a real gate. For high-stakes actions — production database changes, financial transfers, IAM edits — an approve/deny button is worthless, because confirmation fatigue means people click through code they don't understand. So: hardware MFA (physically touch a security key to authorise execution), plus the Vibe Diff.

The Vibe Diff. Before a critical tool runs, an evaluator quorum intercepts the request and translates the generated code back into a plain-English summary — showing the human exactly how their fuzzy original intent maps onto the proposed execution steps. You're not approving a diff. You're approving a translation of your own intent, which is the thing you're actually qualified to judge.

This is the single best idea in the paper and I want it in every tool I use.

Red, Blue, Green — SecOps that runs at agent speed

Application logic is now generated, executed and discarded fast enough that manual security operations can't keep pace. So the operations themselves become agentic, running in parallel with the developer:

  • Red (Agent Attacker) injects adversarial vibes — roleplay jailbreaks, and malicious instructions buried inside large blocks of RAG context or dummy forum posts of the kind developers routinely paste into an IDE. It tests whether the target agent gets distracted by poisoned context and hallucinates an insecure solution.
  • Blue (Agent Defender) replaces traditional UEBA, which doesn't work on non-deterministic systems, with Agent Behavioural Analytics. It baselines expected execution paths and monitors the Runtime Agent Bill of Materials (AgBOM) — a live inventory of tools, models and data sources in use at any given millisecond. Static SBOMs go stale instantly when the agent is generating its own tools.
  • Green (Agent Fixer) handles response. Killing the container is disruptive and can leave connected APIs corrupted, so instead it runs a stateful quarantine: revoke the agent's tool access, freeze its ability to act on the world, preserve short-term memory intact for forensics. Then auto-refactor — rewrite the insecure script and present the patched version back in the IDE.

One operational constraint underpins all of it: restrict agent output to small batch sizes, ideally with a test-driven loop that blocks the agent from modifying tests and implementation simultaneously, so the test stays an objective baseline. Big unreviewable diffs defeat every control above them.

Auditing the agent's mind

You cannot secure what you cannot see. In microservices an HTTP 200 means success; in an agentic system it can mask a hallucination loop cascading quietly in the background. Which introduces Denial of Wallet — adversaries triggering infinite, computationally expensive loops specifically to bankrupt your LLM and cloud billing.

The unit of observability here is the vibe trajectory: API calls, tool inputs and outputs, RAG retrievals, token latency, aggregated through OpenTelemetry into one chronological view of the cognitive steps — logging the leap from the user's prompt all the way to the compiled AST.

Two concepts I'll keep:

  • Intent drift. Trust is a degradable asset. Trust decays when the agent's chain of thought pursues sub-goals diverging from the original request. The example is perfect: "optimise the database query" drifting into downloading a new unauthorised indexing library.
  • Stateful circuit breakers. Generate a version-control checkpoint before any codebase modification. Behavioural analytics score the trajectory against the AgBOM and penalise a dynamic agent trust score; below threshold, the breaker trips, rolls back to the checkpoint, revokes tool access and freezes execution without corrupting connected APIs.

Evaluation: the other half

Why evaluating a vibe coding agent isn't like evaluating other software — three constraints that shape everything:

  1. The underspecification gap. Traditional testing assumes a complete spec exists before evaluation. Here the prompt is inherently underspecified. "Make the dashboard load faster" is not a test case. The first job of evaluation is determining whether the agent reconstructed the right unstated spec.
  2. The user often cannot validate the output. Non-technical users can't review 600 lines. Experienced engineers can't either, in real time. The gap between "the agent thinks it succeeded" and "the code is correct" is wider here than in any other agent category.
  3. The session is iterative and the codebase is state. Every turn modifies real files; bad early decisions compound. Evaluation has to cover the arc of a multi-turn conversation on a living codebase, not just turn-level decisions.

Seven dimensions, split into what the developer feels and what happens invisibly:

# Dimension The question
1 Intent satisfaction Did it build what the user meant, not what they said? Hardest to measure, and what the user actually judges on.
2 Functional correctness Does it build, run, pass tests? The floor — and easy to game by deleting or mocking tests.
3 Visual & behavioural For UI work the artifact is the rendered output, not the code. Code metrics miss the point.
4 Cost & efficiency Tokens, latency, tool calls, and how many corrections before convergence. One turn vs eight is a different product.
5 Code quality & conventions A diff that passes tests but violates house style is a failure even when locally correct.
6 Trajectory quality Did it read related files first, sequence edits coherently, pick the right tool? Correct output from bad reasoning is a fragile success.
7 Self-repair When the build fails or the user says "no, not like that" — does it recover or compound?

Safety and responsible AI is transversal: vulnerabilities, refusal behaviour, content safety, IP exposure, scored alongside every dimension rather than bolted on as a separate gate.

The methods map onto the dimensions rather than replacing each other. Automated functional testing (pytest, jest, eslint, mypy in CI) is the cheapest signal and covers dimension 2 and the rule-checkable parts of 5. Static security analysis (Snyk, Semgrep, git-secrets) plus scripted red-team suites cover the transversal safety layer. LLM-as-judge and agent-as-judge cover the ones rules can't reach — intent satisfaction, style, trajectory. Browser-based testing covers visual and behavioural correctness, because for a rendered page the code is not the artifact.

My one-line summary of the whole paper: security is a boundary, evaluation is a verdict, and shipping without both is how a demo becomes an incident.
