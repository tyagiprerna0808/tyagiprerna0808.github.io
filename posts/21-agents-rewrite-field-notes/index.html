A coda to Vibe Coding & Agents. Posts 16–20 were notes on the first cut of Google’s five-day intensive. Then they published a rewrite — same five days, five different papers — and this is what the second edition adds.

Five new PDFs, same five days

I’d already read the intensive once. Then five more files landed in my downloads folder in a single afternoon, all stamped Rewrite v1, all updated May 2026:

Day First cut (posts 16–20) The rewrite
1 The SDLC paper — vibe coding as a spectrum Introduction to Agents
2 Agent Tools & Interoperability — protocols, A2A Agent Tools — tool design and MCP internals
3 Agent Skills Context Engineering — sessions and memory
4 Vibe coding security & evaluation Agent Quality — observability, tracing, evals
5 Spec-driven development Prototype to Production — CI/CD and AgentOps

Only Day 2 kept its subject, and even there the paper is new — none of the material I wrote up in Post 17 (the N×M collapse, the monolithic ceiling, the GOTO problem) survives into the rewrite. This isn’t a revision. It’s a second edition with a different argument.

Two hundred and seventy-six pages. I read them with the same suspicion I brought to the first cut: a whitepaper written by a cloud vendor is also a product brochure. Roughly every third paragraph ends in a capitalised noun you can put on an invoice — Agent Gateway, Agent Registry, Model Armor, Memory Bank, Agent Runtime.

So: keep the mechanism, discard the SKU. What follows is what was left.

The definition that actually holds

The first edition’s big line was the model is the commodity and the harness is the product. The rewrite goes at the same idea from a different angle, and I think lands it harder:

An agent is the combination of models, tools, an orchestration layer, and runtime services which uses the LM in a loop to accomplish a goal.

Four parts: the model is the brain, tools are the hands, the orchestration layer is the nervous system, deployment is the body and legs. I’d normally roll my eyes at the anatomy metaphor, except it earns its keep across the other four papers — every failure mode they describe slots into exactly one of those boxes.

But the sentence I actually wrote down was this:

An agent is a system dedicated to the art of context window curation. It is a relentless loop of assembling context, prompting the model, observing the result, and then re-assembling a context for the next step.

That reframe does real work. The agent isn’t the model and it isn’t the prompt — it’s the software that decides what the model gets to see on the next call. Memory, RAG, tool results, session history, sub-agent outputs: all of it is just a supplier feeding that one decision.

Which is why the thing I’d have called prompt engineering two years ago now takes up an entire 73-page paper under a different name.

The ladder that ends an argument

Day 1 is new to this edition and its taxonomy is the most immediately useful thing in the stack, because it settles the argument every team has in week one: do we need a multi-agent system?

Level What it is What it can’t do
0 · Core reasoning An LM alone — no tools, no memory Blind to anything after its training cutoff
1 · Connected problem-solver Adds tools — search, RAG, an API Handles one hop, not a plan
2 · Strategic problem-solver Plans multi-step, engineers its own context between steps Still one agent, one head
3 · Collaborative multi-agent A team of specialists; agents treat agents as tools Bounded by today’s reasoning quality
4 · Self-evolving Notices a capability gap and builds the missing tool or agent Mostly still a research frontier

Their Level 2 example is small and I liked it: “find a good coffee shop halfway between my office and my client’s office.” The agent calls maps, gets back “Millbrae,” and then — this is the bit — constructs a new, narrower query for the next tool: query="coffee shop in Millbrae, CA", min_rating=4.0.

Nothing about that is impressive as software. But that small act of rewriting its own next input is exactly the line between “calls a tool” and “has a plan.” It’s the smallest observable unit of context engineering, and you can point at it in a trace.

Level 3 carries the honest note, and to their credit they say it out loud: collaborative multi-agent systems are “currently constrained by the reasoning limitations of today’s LMs.” A vendor telling you the exciting tier isn’t ready is worth slightly more trust than the rest of the document.

The eighty percent nobody demos

Day 5 opens with the number this whole series keeps circling:

Roughly 80% of the effort is spent not on the agent’s core intelligence, but on the infrastructure, security, and validation needed to make it reliable and safe.

They call it the last-mile production gap, and then do something most writing on this refuses to do: list the failures concretely instead of gesturing at “challenges.”

  • A support agent is talked into giving products away free, because nobody wired the guardrails.
  • A user reaches a confidential internal database through the agent, because auth was misconfigured.
  • An agent runs up a large bill over a weekend and no one can say why, because there was no monitoring.
  • An agent that worked yesterday silently stops working, because there was no continuous evaluation.

Read those again and notice what they share: not one is a model quality problem. Every one is an ops problem wearing an AI costume — which is the same conclusion Shipping It arrives at from the ML side, and the reason that half of my notes takes longer than the modelling half.

The operating discipline they propose is a loop: Observe → Act → Evolve. Observe is the three pillars — logs are the diary, traces are the narrative, metrics are the report card. Act is the reflexes: circuit-breaker a misbehaving tool with a feature flag, route suspicious traffic to a human review queue. Evolve is the part I’d underrate: turn every production failure into a permanent test case, then ship the fix through the same pipeline.

The gate that makes it work is evaluation-gated deployment — no version reaches users without passing an eval suite, either as a report linked in the PR or as a pipeline stage that blocks the merge. And the rollout patterns are the boring, correct ones: canary at 1%, blue-green, A/B on real business metrics, feature flags. All of which rest on versioning everything — prompts, tool schemas, model endpoints, memory structures, and the eval datasets themselves.

The trajectory is the truth

Day 4 replaces the first edition’s security-and-evaluation paper, and where Post 19 came at evaluation through the security door, this one comes at it through QA. Its thesis fits in a line — agent quality is an architectural pillar, not a final testing phase — and its sharpest observation is this:

An agent can pass 100 unit tests and still fail catastrophically in production, because its failure isn’t a bug in the code; it’s a flaw in its judgment.

That’s the part traditional QA has no vocabulary for. A crash is loud. An agent failure is quiet: the service stays up, the API returns 200 OK, the output looks plausible, and the answer is wrong. You cannot set a breakpoint on a hallucination.

So the unit of evaluation moves. Not the output — the trajectory: thought → action → observation → thought. And they’re specific about why a single output score can’t catch it: a small stochastic word choice at step 1 can send the agent down an unrecoverable path by step 4.

The framework they hang on that is four pillars, and it’s genuinely good:

Pillar The question it asks
Effectiveness Did it achieve the user’s actual intent? Not “did it write code” but “did the code produce the right insight”
Efficiency Did it solve it well? 25 steps, five failed tool calls and three self-corrections to book one flight is a low-quality success
Robustness When the API times out and the data is missing, does it degrade gracefully and report what it couldn’t do?
Safety Does it stay inside its boundaries under prompt injection and refuse what it should refuse?

And then the sentence that stops the pillars from being a poster:

You cannot measure Efficiency if you don’t count the steps. You cannot diagnose a Robustness failure if you don’t know which API call failed. You cannot verify Safety if you cannot inspect the agent’s internal reasoning.

Observability isn’t downstream of evaluation. It’s the precondition for it. Without the trace you are grading a process you never saw.

The failure taxonomy for reading that trace is worth stealing wholesale, because it turns “the answer is wrong” into “the answer is wrong because”: bad plan, wrong tool, right tool with malformed arguments, or — the nasty one — a correct tool call whose result the agent then misread, including sailing straight past a 404 as though it had succeeded.

Tools are a writing problem

Day 2 surprised me most, because the best advice in it is editorial, not architectural. Tool definitions enter the model’s context as prose, which makes tool design technical writing with a runtime.

Four rules I’m keeping:

Publish tasks, not API calls. A thin wrapper over an enterprise API with forty optional parameters is written for a human developer who already knows the domain. A tool is called at runtime by something that has to guess. Wrap the task the agent needs to perform, not the endpoint you happen to have.

Describe what, not how. System instructions should say “create a bug to describe the issue,” never “use the create_bug tool.” Naming tools in the prompt couples your instructions to your implementation — and under MCP the available tools can change beneath you at runtime.

Name things like you’ll read them in an audit log. create_critical_bug_in_jira_with_priority beats update_jira — for model accuracy first, and for the incident review second.

Error messages are prompts. This is the one I’d never thought about properly. A tool’s error goes straight back into the model’s context, so a bare status code wastes a turn. Compare:

"Failed to fetch weather data: API rate limit exceeded.
 Wait 15 seconds before calling this tool again."

…against a plain 429. The first is a recovery instruction the model can act on. Your error strings are part of your prompt surface whether you designed them that way or not.

MCP, with the marketing removed

Post 17 covered why MCP exists — N models times M tools, and the custom connector for every pairing. The rewrite spends its pages somewhere more useful: on what the protocol actually is in the field. It includes a table I hadn’t seen anywhere else — real client support for each part of the spec, measured across publicly tracked MCP clients in September 2025:

Capability Clients supporting it
Tools 99%
Resources 34%
Prompts 32%
Sampling 10%
Elicitation 4%
Roots 5%

So in practice, MCP is Tools. The other five primitives are a spec that mostly hasn’t shipped. That one table is worth more to an architecture decision than the twenty pages describing what those primitives could theoretically do.

Two risks stuck with me. The first is tool shadowing, and the example is beautifully mundane. A legitimate server offers secure_storage_service, described narrowly: use only when the user asks to save a secret. A malicious local server offers save_secure_note, described greedily: “use this whenever the user mentions save, store, keep, or remember.” No exploit, no CVE. The attacker simply wrote a better tool description and the planner picked it. Prompt injection where the payload is documentation.

The second is quieter and will bite more people: context window bloat. Every tool definition from every connected server must sit in the context for the model to know it exists. Connect enough servers and the manifest crowds out the actual task — cost up, latency up, and reasoning quality down, because the model now has to find the right tool in a haystack it didn’t ask for.

Their proposed fix made me sit up: RAG for tool discovery. Retrieve the handful of relevant tools first, then load only those definitions. A lovely idea with an obvious sharp edge, which they flag themselves — poison the retrieval index and you have poisoned tool selection.

Sessions, memory, and context rot

Day 3 is the paper with no counterpart in the first edition, and it draws a line I’d been blurring. A session is the workbench: the chronological events and mutable state of one conversation. Memory is the filing cabinet: extracted, consolidated, framework-agnostic facts that outlive the session. Raw transcript is not memory. Memory is what you kept after you threw the transcript away.

The distinction between memory and RAG is the cleanest I’ve read:

RAG is the agent’s research librarian — a shared, static, authoritative knowledge base. Memory is its personal assistant — a private notebook, scoped per user, dynamic and uncertain. RAG makes an agent an expert on facts; memory makes it an expert on the user.

That also explains the isolation asymmetry that catches people in production: RAG indexes are usually shared by design, memory is almost always scoped per-user, and confusing the two is how one customer ends up reading another’s history.

And then context rot — the term I’m adopting immediately. Not the hard context-window limit, but the softer failure: as context grows, the model’s ability to attend to the critical part of it decays. More tokens, worse answers, higher bill. Long-context models don’t repeal this; they move the wall.

So you compact — sliding window, token-based truncation, or recursive summarisation — and the operational note that comes with it is the part I’d have got wrong: run the expensive summarisation asynchronously and persist the result, and keep a record of which events each summary already covers, so you never pay to send them twice.

What I’d push back on

Three things, in fairness to the reader.

The 80% number has no citation. It’s offered as “what we consistently observe in practice with customers.” I believe the shape of it — it matches every ML system I’ve shipped — but it’s an anecdote in a lab coat, and it does a lot of rhetorical work in that paper.

Every problem resolves to a product. Sprawl → Agent Registry. Injection → Model Armor. Identity → Agent Identity. The problems are real and well described; the implicit claim that the answer is a managed service is the part you should price yourself.

Level 4 is a story, not a spec. The self-evolving agent that notices a capability gap and builds its own tool is described with the same confidence as the parts that ship with code samples. It doesn’t have code samples. Read that chapter as a roadmap, not a report.

What I’m taking into the build

Four sentences survived both editions, and they’re the ones I’ll be building against:

  1. The agent is the context curator, not the model. Design what the model sees on turn n+1.
  2. Evaluate the trajectory, not the answer. If you can’t count the steps, you can’t claim efficiency.
  3. Tool descriptions and error strings are prompt surface. Write them like it.
  4. Assume 80% of the work starts after it demos well, and structure the project so that 80% isn’t a surprise.

None of that needs a framework, a platform, or a purchase order. Which is the point — and the reason the next thing I write is forty lines of Python instead of a diagram.
