Part 3 of Vibe Coding & Agents. Notes on Agent Skills by Tanvi Singhal, Gabriela Hernandez Larios, Debanshu Dus, Lavi Nigam and Smitha Kolan.

A skill is a folder with a SKILL.md in it. That's the whole primitive. Which is either underwhelming or the most interesting thing in the five papers, depending on how much time you've lost to prompt files that grew to four hundred lines.

The claim is that skills are the first credible procedural memory for LLM agents. Models already have workable analogues for remembering what happened (episodic) and remembering facts (semantic). What they've lacked is remembering how to do a thing, step by step. That's the gap.

Anatomy, and the trick that makes it work

The canonical layout — only SKILL.md is mandatory, everything else is optional:

cafe-preparation/
  SKILL.md              # metadata + instructions  (required)
  scripts/              # executable code, any language
    calc_quantities.py
  references/           # supplementary context, loaded on demand
    menu_and_recipes.md
  assets/               # templates, configs, schemas
    prep_sheet_template.md

The innovation isn't the folder. It's progressive disclosure, in three levels:

  1. Metadata — name and description — is always in context.
  2. The SKILL.md body loads only when the skill triggers.
  3. Bundled resources load strictly as needed, and scripts execute without ever entering the token window.

So a hundred installed skills costs roughly 100 × 50 ≈ 5,000 tokens of always-loaded metadata, and you pay the real cost only for the one that fired. That is the entire economic argument, and it's a good one.

Rule of thumb from the paper: if the SKILL.md is getting long, the next paragraph probably belongs in references/, not in the body.

Two paths produce these. Path A is a subject-matter expert translating what they already have — a compliance officer with a thirty-page runbook, an HR manager with onboarding guides. No coding required; the content exists, it just needs a format the agent can route on. Path B is crystallising what the agent just did: it completed a non-trivial repeatable task, so you have it draft the skill and you review instead of authoring. Both produce the same artifact.

The description field is the routing algorithm

This is the part I got wrong first and the paper is blunt about. The description in the YAML frontmatter is the only thing the model sees when deciding whether to load the skill. State what it does, front-load trigger keywords, be pushy if the model under-triggers, and explicitly say what it is not for:

---
name: cafe-preparation
description: |
  Calculates daily ingredient needs and generates prep sheets for cafe operations.
  Use when the user asks to estimate daily quantities, convert drinks to
  ingredients, or generate shopping lists.
  Do NOT use for employee shift scheduling or financial accounting.
---

Naming convention: boring and obvious. snake_case for directories, kebab-case for skill names, gerund form where it reads naturally (managing-databases). Never utils or tools, and no internal jargon.

To hit the industry-standard ~90% trigger accuracy, the description has to pass four checks: testable specificity (write three positive and three negative triggers), clarity (ambiguous queries don't overlap adjacent skills), execution fidelity (describes actual behaviour, not aspirational), and rephrasing stability (routes the same however the user phrases it).

The number that should worry you

An Agent Skill without a test is a hope, not a capability.

SkillsBench (2025) benchmarked 84 real-world agent tasks and found 19% performed worse with a skill than without one. Not neutral. Actively degrading.

Vercel's production analysis is more specific and more uncomfortable: a 56% non-invocation rate for skills expected to fire consistently, and a skill stripped of its instructions scored 58% while the agent with no skill at all scored 63%. A five-point deficit from adding something.

The same study found a passive AGENTS.md index of project conventions hit a 100% pass rate against a 53% baseline — which is the cleanest statement of the boundary I've seen. Global context belongs in always-loaded documentation. Skills are for narrow, action-specific workflows. Reaching for a skill when you needed a line in AGENTS.md is a real and costly mistake.

Four failure modes, and they surface in different places:

Failure What happens Where you see it
Trigger Wrong skill fires, or the right one doesn't Routing logs
Execution Triggers correctly, produces wrong output or errant tool calls Output quality
Token budget A large body crowds context, degrading unrelated turns Only under realistic context load
Regression A new skill overlaps an existing one and breaks routing Only with the full library exercised together

The bottom two only appear when multiple skills interact under production load. Which leads to the sentence I've written on a sticky note:

Isolation is a trap

Never evaluate a skill purely on its own. Production agents co-load 5 to 15 skills simultaneously. A body over ~5,000 tokens can work perfectly alone and cause context rot the moment it has company. MCPVerse measured an 18.2% accuracy drop from tool proliferation and attention competition; Chroma Research found all frontier models degrade as input grows, especially with co-loaded noise.

Passing an isolated test is a false positive for production readiness. That's the trap.

The related trap is what the paper calls the evaluation illusion: trajectory testing scores the composite system — host agent plus skill — so when a multi-skill trajectory fails you often can't decouple routing from instruction quality from execution. The fix is a two-tiered assert: validate the tool code independently, and audit the SKILL.md triggers across multiple model families so you catch descriptions that are quietly locked to one architecture.

Evaluation-driven development

Invert the workflow: write three JSON eval cases — input, expected tools, expected output — before drafting the SKILL.md. Drafting them upfront surfaces description ambiguities and trajectory errors before they compound into the body.

{
  "case_id": "refund_dup_charge_001",
  "input": "I was charged twice for order #4521 last Tuesday",
  "expected_skill": "refund_processor",
  "expected_tool_calls": [
    {"tool": "lookup_order", "args": {"order_id": "4521"}},
    {"tool": "check_duplicate_charge", "args": {"order_id": "4521"}}
  ],
  "expected_output_format": "confirmation_with_refund_id",
  "rubric": ["acknowledges duplicate", "cites order id", "provides next step"]
}

Then score the output and the trajectory separately. Latitude's March 2026 analysis found final-output-only scoring passes 20–40% more cases than trajectory-aware scoring. That gap is entirely instances where the agent reached the right answer via the wrong sequence of tool calls. Tolerable read-only. Not tolerable when the tools have side effects.

Two non-negotiables when using LLM-as-judge at scale: swap the positions of reference and actual output to kill ordering bias, and calibrate against human ratings until you reach 90% agreement.

Graduation tiers, and pass^k

Skills earn authority in tiers rather than shipping at full permission:

  • Read-only — LLM-as-judge eval, 90% trigger accuracy.
  • Draft-only (human review) — golden dataset of 20+ cases, human approval.
  • Action-allowed — full adversarial red-teaming, no rollback events, and sustained pass^k.

pass^k runs the eval k times and requires success on every run. The illustration is brutal: on τ-bench, GPT-4o scored 61% at pass^1 and dropped below 25% at pass^8. Single-run success is a poor predictor of production reliability, which is something I already believed about models and had not thought to apply to a markdown file.

Two calibration adjustments the paper insists on: production performance typically drops 20–30% against offline pass@1 benchmarks (ReliabilityBench), and simulation-based evaluation carries an optimistic bias of up to 9%. So human review of representative outputs stays the ultimate signal for action-allowed graduation.

Skills vs MCP vs AGENTS.md

They compose; they don't compete.

  • MCP is reach. It connects the agent to an external system — Drive, Salesforce, BigQuery, an internal API.
  • A skill is know-how. It teaches the agent how to think about a kind of work. When it needs data, it tells the agent to call a tool — usually one an MCP server provides.
  • AGENTS.md is always loaded. Skills load on demand. Keep AGENTS.md tight — conventions, stack, build commands — and optionally use it as a router, with a short catalog at the bottom telling the agent what's in the library.

And the honest caveat the paper puts in bold: skills do not kill multi-agent architectures. Multi-agent is still right for genuine parallelism, real capability boundaries (different access, different security postures), hierarchical decomposition where the abstraction layers actually differ, adversarial check-and-balance setups, and heterogeneous models. What skills did was add a missing primitive, so systems that were multi-agent by default can now be single-agent-with-skills by design.

The worked example that sold me: a logistics company with 100 process variants. One giant context window rots. RAG over the runbooks means running a vector DB, an embedding model and a chunking strategy whose quality has nothing to do with the procedures. A hundred sub-agents is a hundred deployments and a hundred eval surfaces. One agent with a hundred skills costs ~5,000 tokens of metadata, keeps procedures in version control, and makes the 101st variant a new folder rather than a new deployment.

The 98.4% number

One finding I keep coming back to. A reverse-engineering of Claude Code v2.1.88 (Liu, Zhao, Shang and Shen, 2026) found 98.4% of the codebase is operational infrastructure — permission classifiers, context compaction pipelines, subagent delegation, session storage — and 1.6% is the agent loop itself. The model sits behind a remote API.

That is Day 1's agent = model + harness claim with a measurement attached. As baseline reasoning converges across foundation models, the differentiator for reliability is the deterministic engineering around the model. And inside that engineering, the unit you compose and reuse is the skill.

Which is why the paper's table on improvement styles is the one I'd show a manager: a model swap takes days to weeks and only the platform team can do it. A fine-tune takes weeks to months and only the ML team can do it. A new skill takes hours to days, any domain team can do it, and the context cost is dynamic — paid only on matching turns.
